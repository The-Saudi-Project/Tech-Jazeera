Executive assessment
The app has meaningful security controls and working operational flows, but it is not ready for an
unconditional production handoff. Three confirmed High-severity blockers are outsourced-personnel
disclosure to Worker accounts, accidental clearing of employee document metadata, and settlement
numeric corruption. There are 19 confirmed findings: 0 Critical, 3 High, 14 Medium and 2 Low. These are
all quality findings, not 19 exploitable security vulnerabilities. The direct security findings are S01 (High) and
S02 (Medium); A01 is an inconsistent authorization policy that blocks intended access.
The most useful speed work is batching target-report database queries, correcting shared-IP throttling,
bounding API waits and paginating outsourced lists. Deleting small unused functions is housekeeping and is
not supported as a cause of production slowness.
Your repositories are correctly recognized as server/ and client/, each with real history (174 and 250
commits respectively at the inspected heads). Root history is archived and is not the active deployment
repository. No Git setup or reinitialization is needed. Both repos have READMEs and architecture/history
documentation; the issue is stale claims, not a lack of documentation.

exist; Section Access grants come from approval-role membership; employee/team and record-owner

legacy role-specific actions should be documented rather than replaced indiscriminately with section

S01 - Worker accounts can read outsourced-worker PII and
private documents
ID: S01
Severity: High
Category: Security
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/modules/employees/outsourcedEmployee.routes.js:29;
server/src/modules/employees/outsourcedEmployee.service.js:17
Component / API / data: GET /api/outsourced-employees; GET /api/outsourced-employees/:id; GET
/api/outsourced-employees/:id/documents/:fileId/file; OutsourcedEmployee
Evidence: .qa-audit/production-2026-10-04/http-evidence.json;
.qa-audit/production-2026-10-04/deep-evidence.json. Worker list/detail returned 200. File route returned
200 and synthetic private bytes through the real auth/controller/service chain; only the external CDN fetch
was stubbed.
What is happening / root cause: The client hides this section using employeeCreate, but these backend
reads have authentication only. Neither a read permission nor record visibility is applied. The raw list limit
also accepts 1,000,000 and returned all 1,201 synthetic records.
Why it matters / impact: Security: high confidentiality impact. Business: personnel/identity data exposure.
Users: all outsourced workers in this collection. Likelihood: high with any Worker account. Exploitability:
direct API request, no elevated role. Production: release blocker if this code is deployed.
How to reproduce: Log in as the disposable Worker. GET the collection and a seeded record ID, then its
document file endpoint. Run http-tests.mjs and deep-tests.mjs against the isolated runtime. Do not repeat
against real personnel records.
Recommended fix / architecture: Apply an explicit approved read policy to list, detail and file routes,
including any required team/client scope. Reuse that policy in the client guard. Add a Zod query schema
with a small maximum page size and project only needed list fields. Keep file authorization before
signing/fetching.
Priority: P0 - before release.
Regression test required / verification: YES - Worker denied on all three paths; allowed role succeeds;
forbidden coordinator denied; invalid/excessive list limits rejected; file bytes inaccessible through both
record and download URLs.



S02 - Forced password change is enforced only by the UI
ID: S02
Severity: Medium
Category: Security
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/middleware/auth.js:34
Component / API / data: requireAuth; authenticated API endpoints; User
Evidence: .qa-audit/production-2026-10-04/latest-regressions.json: weak-password login returned
forcePasswordChange:true; its bearer token still fetched /api/me/profile with 200.
What is happening / root cause: Authentication loads the user but does not restrict a
forcePasswordChange session. Closing/bypassing the frontend flow is unnecessary: the API token already
works.
Why it matters / impact: Security: password-remediation control bypass. Business/users: account remains
usable with a credential the system says must change. Likelihood: medium, conditional on a flagged account.
Exploitability: direct authenticated request; this does not grant a higher role.
How to reproduce: Use a disposable flagged/weak-password account, POST /api/auth/login, then GET
/api/me/profile using the returned token without changing its password. See latest-regressions.mjs.
Recommended fix / architecture: Issue a restricted password-change session or reject normal protected
endpoints while the flag is set. Explicitly allow password change and logout, and return a stable
machine-readable code that the UI handles.
Priority: P1 - next remediation cycle.
Regression test required / verification: YES - flagged token cannot access normal resources; password
change clears the restriction; logout still works; ordinary users remain unaffected.

F01 - Partial employee edits silently clear additional-document
metadata
ID: F01
Severity: High
Category: Functional Bugs
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/modules/employees/employee.validation.js:94;
server/src/modules/employees/employee.validation.js:187
Component / API / data: PATCH /api/employees/:id; Employee.additionalDocuments
Evidence: .qa-audit/production-2026-10-04/latest-regressions.json: updating only department returned
additionalDocuments:[]. Rechecked the latest on-disk schema on October 5: parse({department:'Audit'}) also
emitted additionalDocuments:[].
What is happening / root cause: The shared schema applies default([]) to additionalDocuments. Deriving
the PATCH schema with partial() still materializes that default under the installed Zod version. The service
writes the resulting empty array.
Why it matters / impact: Security: integrity rather than access-control issue. Business: document-register
metadata loss. Users: any employee edited through a partial payload. Likelihood: high in normal partial
updates. Exploitability: ordinary authorized PATCH. Production: release blocker; binary file deletion was not
demonstrated.
How to reproduce: Seed an employee with one additional document. PATCH only {"department":"QA
department"}. Read the employee and compare the array. latest-regressions.mjs records the HTTP proof.
Recommended fix / architecture: Remove create defaults from the shared PATCH object. Apply defaults
only in create-specific schema/service and make updates preserve omitted keys. Review sibling optional
defaults before changing them.
Priority: P0 - before release.
Regression test required / verification: YES - omitted documents survive PATCH; explicit [] clears only
when requested; creation still gets the intended default; nested omitted fields are retained.



F02 - Settlement overrides can persist Infinity as financial
amounts
ID: F02
Severity: High
Category: Functional Bugs
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/modules/eosb/settlement.validation.js:19;
server/src/modules/eosb/settlement.service.js:24
Component / API / data: POST /api/eosb; Settlement monetary fields
Evidence: .qa-audit/production-2026-10-04/latest-regressions.json: overrideEosbGross:1e308 returned 201
with null monetary values in JSON; direct database check showed non-finite eosbGross and totalSettlement.
What is happening / root cause: An input may be finite while rounding by multiplying it by 100 overflows.
The override has a minimum but no business maximum; computed values are persisted without a
finite-value invariant.
Why it matters / impact: Security: integrity risk to an authorized financial workflow. Business: corrupted
settlement totals/PDF/report inputs. Users: settlement operators and employees. Likelihood: low
accidentally, easy with a crafted authorized request. Production: release blocker.
How to reproduce: POST /api/eosb for a disposable eligible employee with exitDate:2026-09-30,
exitReason:EndOfContract, overrideEosbGross:1e308. Inspect both response and stored finite checks. See
latest-regressions.mjs.
Recommended fix / architecture: Set realistic monetary/day bounds; validate every computed amount
with Number.isFinite before persistence; use a consistent decimal or bounded minor-unit representation.
Reject invalid results with 400/422 rather than storing them.
Priority: P0 - before release.
Regression test required / verification: YES - extreme finite values are rejected with no write; boundaries
and normal rounding pass; all saved settlement amounts are finite.



F03 - Concurrent final-settlement creation stores duplicates
ID: F03
Severity: Medium
Category: Functional Bugs
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/modules/eosb/settlement.service.js:100;
server/src/modules/eosb/settlement.service.js:139
Component / API / data: POST /api/eosb; Settlement
Evidence: .qa-audit/production-2026-10-04/latest-regressions.json: five concurrent EndOfContract requests
returned five 201 responses; five settlements existed for one employee.
What is happening / root cause: The existing-record check and insertion are separate operations without a
database uniqueness invariant. Latest edits exclude CurrentEmployee simulations from the lookup, but do
not remove the final-settlement race.
Why it matters / impact: Security: data-integrity issue for authorized callers. Business: duplicate
liabilities/review work, not proof of duplicate cash payout. Users: HR/accounts. Likelihood: medium with
retries/double-submit. Exploitability: simultaneous authorized requests.
How to reproduce: Send five parallel identical final-settlement requests for one fresh employee. Count
stored final settlements. See latest-regressions.mjs.
Recommended fix / architecture: Agree the final-settlement identity (employee plus employment episode
if rehiring is supported). Enforce it with a suitable partial unique index that excludes CurrentEmployee
simulations, plus idempotency and 409 handling. Reconcile existing duplicates before adding the index.
Priority: P1 - next remediation cycle.
Regression test required / verification: YES - concurrency stores exactly one final settlement; retried
idempotency key returns the same result; simulations remain allowed; distinct employment episodes follow
policy.

F05 - Leave entitlement combines requests from different
future years
ID: F05
Severity: Medium
Category: Functional Bugs
Status: CONFIRMED on the tested local snapshot.
Location / file / line: server/src/modules/leave/leave.service.js:89
Component / API / data: POST /api/me/leave; annual eligibility / LeaveRequest aggregation
Evidence: .qa-audit/production-2026-10-04/deep-evidence.json: a two-day annual allowance
auto-approved June 2027; June 2028 then saw usedDays:2 and remainingDays:0 from the same 2026-based
window.
What is happening / root cause: Eligibility uses the current service-year start and a lower-bound-only date
filter. Future requests from different entitlement periods are pooled together.
Why it matters / impact: Security: entitlement integrity. Business/users: wrong automatic approval/review
decisions and balances. Likelihood: medium when advance leave is allowed. Exploitability: ordinary request
dates. Production: incorrect HR workflow.
How to reproduce: Create Annual policy with daysPerYear:2. Submit two days in June 2027, then two days
in June 2028 for the same employee. See deep-tests.mjs.
Recommended fix / architecture: Define the entitlement period relative to the requested leave and bound
both ends. Specify handling of cross-period leave and future booking limits. Preserve decision snapshots,
while recomputing a fresh eligibility assessment for new requests.
Priority: P1 - next remediation cycle.
